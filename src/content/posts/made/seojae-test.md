검증은 실제 문서로 했어요. 한국어 업무 문서 576건(마크다운 281, 워드 294, 21MB)을 첫 책장으로 넣고, 검색이 맞는지, 힌트가 제때 붙는지, 파일을 넣으면 몇 초 만에 잡히는지, 옮기면 안 되는 곳으로 옮기려 할 때 거부하는지를 쟀어요. 통과한 것도 놓친 것도 그대로 적어요. 그리고 한 번 재고 믿으면 안 되는 숫자가 하나 있었어요.

## 검색 정확도

문서가 쓰는 말로 물은 질문과 다른 말로 물은 질문을 섞었어요.

| 질문 | 검색어별 문서 수 | 힌트 | 판정 |
|---|---|---|---|
| 예외 처리는 어떻게 해야 하나 | 예외 269, 처리 389 | 없음 | 맞음 |
| omm 파일 문법 | omm 540, 파일 560, 문법 9 | 없음 | 맞음 |
| 리프레시 데이 정책 | 리프레시 0, 데이 0, 정책 19 | 붙음 | 맞음 |
| 블록체인 합의 알고리즘 | 블록체인 0, 합의 25, 알고리즘 0 | 붙음 | 맞음 |
| 에러 났을 때 어떻게 처리하지 | 에러 27, 처리 389 | 없음 | 놓침 |
| 데이터베이스 접근 계층 | 데이터베이스 0, 접근 28, 계층 258 | 없음 | 놓침 |

위 넷은 통과예요. 문서가 쓰는 말이면 정확한 절이 1위고, 서재와 겉도는 질문이면 "이 서재가 쓰지 않는 말"이라는 힌트가 붙어요. 재검색 힌트는 오탐 0건이에요.

아래 둘은 놓쳤어요. "에러"는 27개 문서에 실제로 있고 문서가 주로 쓰는 말은 "예외"예요. 단어가 색인에 있긴 한데 엉뚱한 문서에 있는 경우라 빈도만으로는 못 잡아요. 이건 설계 글에서 이미 "BM25의 한계"로 적은 것이고, 테스트는 그 한계가 어디까지인지를 확인했어요.

## 버린 규칙이 왜 틀렸는지도 실측으로

재검색 힌트 규칙 둘을 폐기한 근거가 이 테스트예요. "색인에 없는 말이 하나라도 섞이면"은 "연차 휴가 며칠"에서 "며칠"이 없다고 힌트를 붙였는데 검색은 정확했어요. "검색어가 전부 흔한 말이면"은 "예외 처리"에서 둘 다 47%, 68%로 흔하다고 힌트를 붙였는데 역시 정확했어요. 둘 다 정상 검색에 오탐을 냈고, 오탐을 내는 유도 장치는 없느니만 못해요.

## 파일 감시

MCP 서버를 띄워 둔 채 재색인 명령 없이 파일을 넣고 고치고 지웠어요.

| 동작 | 검색에 반영되기까지 |
|---|---|
| 파일 생성 | 1.3초 |
| 파일 수정 | 1.3초 |
| 파일 삭제 | 0.2초 |

1.3초는 디바운스 1초 때문이에요. 에디터가 저장 한 번에 이벤트를 여러 개 뱉어서, 마지막 이벤트 뒤 1초 잠잠하면 한 번만 처리해요. 삭제는 기다리지 않아요. 지운 파일이 검색에 남아 있는 쪽이 더 나쁘니까요.

## 파일 이동 거부

파일을 실제로 옮기는 코드라 거부 테스트가 제일 많아요. 전부 거부되고 원본은 미분류 폴더에 그대로 남는 걸 확인했어요.

- 책장 이름에 `..`이 든 경로 탈출
- 책장 아래 하위 폴더로 보내기
- 예약어(미분류 폴더 이름)를 책장으로 지정
- 없는 책장으로 보내기(만들기 플래그 없이). 이때는 있는 책장 목록을 돌려줘요.

## 웹 UI와 Claude가 같은 걸 보나

웹 UI는 "Claude가 답한 근거를 같은 검색어로 재현하는 자리"예요. 따로 만든 검색이면 흉내일 뿐이라, 테스트가 두 결과를 직접 비교해요.

```python
web = client.get("/api/search", params={"q": query}).json()
direct = search(conn, query)            # Claude가 쓰는 그 함수
assert [r["source"] for r in web["results"]] == [h.source for h in direct]
```

## 패키지와 보안

빌드한 휠을 저장소 밖에서 `uvx --from` 으로 실행해 초기화, 재색인, 상태, 검색, 미분류 목록이 전부 되는지, MCP 서버가 뜨고 도구가 노출되고 안내문이 주입되는지, 웹 UI가 패키지에 든 정적 파일을 서빙하는지 봤어요. 외부 IP로 접속하면 거부되는 것도 확인했어요.

보안은 실측으로 구멍을 찾았어요. 로컬 서버에 인증이 없는데 브라우저는 아무 페이지에서나 localhost로 요청을 보내는 것 자체는 막지 않아요. 악성 Origin을 단 폼 전송으로 실제로 파일이 심어졌어요. Origin이 있는데 localhost가 아니면 403으로 막고, Origin이 없는 요청(사용자 본인의 도구)은 통과시키는 걸로 고쳤어요.

## 한 번 재고 믿으면 안 되는 숫자

색인 시간이에요. 같은 576건을 두 곳에서 색인했더니 106초와 231초로 2배 넘게 차이가 났어요. 백신 실시간 검사 강도나 같이 돌던 프로세스 때문일 수 있는데, 원인을 단정하지 않기로 했어요. 확실한 건 하나예요. 처음 한 번은 어차피 한 번이고, 중요한 숫자는 증분 재색인 0.6~1.2초예요.

"서재가 있을 때와 없을 때 Claude가 읽는 양"도 쟀어요. 검색으로 필요한 대목만 건네면 파일 전문보다 평균 22배 적었어요. 다만 비교 기준이 서재 없는 쪽에 유리하게 잡혀 있고(어느 파일인지 이미 안다고 가정), 문서를 펼치면 절감이 사라지니, 실제 값은 두 극단 사이예요. 그래서 대출 기록을 만들어 검색 몇 회에 펼침 몇 회인지 쌓기로 했어요.

## 검증에 쓴 명령

```bash
uv run pytest
uvx seojae-mcp reindex 내서재
uvx seojae-mcp search 내서재 "연차 휴가 며칠" -k 2
uv run python bench/measure.py
```

단위 테스트는 경로 탈출, 파서별 형식, 파일 감시, 정리 축 거부, 웹과 MCP 결과 일치, 버전 단일화까지 있어요. 측정 스크립트는 같은 질문을 매번 던져서 값이 바뀌면 알아채게 해요.

## 남는 것

동의어 불일치 두 건은 고친 게 아니라 "아직 못 고친 것"으로 둬요. 힌트 규칙을 느슨하게 하면 오탐이 는다는 걸 이미 쟀으니까요. 다음 후보는 동시출현 기반 용어 확장이에요. 모델 없이 SQL만으로 되고, 임베딩보다 먼저 시도해 볼 값어치가 있어요.

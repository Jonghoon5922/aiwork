토큰빌의 로컬 도구는 세 겹으로 확인했어요. 바뀌면 안 되는 규칙은 단위 테스트 21개로, 창 여러 개가 동시에 붙는 상황은 진짜 프로세스를 띄우는 스모크 테스트로, 화면은 한국어·영어 × 연동·미연동 네 조합을 하나씩 열어서 봤어요. 단위 테스트는 전부 통과했고, 화면 쪽은 지금도 사람 눈(정확히는 DOM 검사)에 기대고 있어요.

이 글은 `npx` 로 설치하는 로컬 도구(업로더, 대화 뷰어, 작업 보드, 스킬·MCP 관리기) 쪽 검증만 다뤄요.

## 무엇을 테스트로 묶었나

전부를 테스트하지 않았어요. **틀리면 사용자의 기록이 망가지거나 비밀값이 새는 곳**만 골랐어요.

작업 보드의 스프린트가 그런 곳이에요. 기간을 정하면 그 기간에 시작한 일감이 저절로 묶이는 기능인데, 규칙이 생각보다 많아요. 테스트 이름이 곧 규칙이에요.

- 시작일이 기간에 들면 저절로 묶이고, 겹치는 기간은 거절한다
- 옮기면 한 줄로 남고, 상태를 바꿔도 풀리지 않으며, 스프린트를 지우면 풀린다
- 날짜로 들어갈 곳을 고르면 적지 않고, '없음'이면 스프린트 밖이다

두 번째 줄이 중요해요. 일감의 제목이나 상태를 고칠 때 파일을 통째로 다시 쓰는데, 그때 사람이 옮겨 둔 스프린트 표시가 같이 지워지면 안 되거든요. 이런 건 화면을 눌러 봐서는 잘 안 보여요. 테스트로 박아 두어야 해요.

```js
test("스프린트: 시작일이 기간에 들면 저절로 묶이고, 겹치는 기간은 거절한다", () => {
  const today = core.now().slice(0, 10);
  const t = core.createTask("일", "", "p");
  const s1 = core.createSprint("p", { name: "이번", start: today, end: today });
  assert.equal(core.getTask(t.ref).sprint, s1.id);
  assert.throws(() => core.createSprint("p", { start: today, end: today }), /겹친다/);
});
```

스킬·MCP 관리기는 보안 쪽을 테스트로 묶었어요. 이 도구는 PC에 흩어진 MCP 설정을 모아 화면에 보여 주는데, 설정에는 토큰이 들어 있어요. 그래서 처음 넣은 테스트 세 개가 전부 "새면 안 되는 것"을 봐요.

- 스킬 설치는 `SKILL.md` 가 없는 폴더를 거절하고, 이름에 상위 폴더로 빠져나가는 표기가 있으면 거절한다
- 다른 PC로 옮길 때 쓰는 MCP 템플릿은 토큰 값을 자리표시자로 바꾸고, 플래그는 남긴다
- 스캔 결과 전체를 문자열로 바꿔 훑었을 때 원문 토큰이 하나도 없다

세 번째가 제일 마음에 들어요. 가리는 함수를 하나하나 검사하는 대신, **결과 전체에 토큰 모양이 남아 있는지**를 봐요. 가리는 걸 깜빡한 경로가 새로 생겨도 이 테스트가 잡아요.

하나 더 있어요. 작업 보드는 먼저 만든 Python 판과 기록 형식이 같아야 해요. 그래서 "Python 판이 쓴 세션 파일을 그대로 읽는다"는 테스트가 있어요. 두 구현이 같은 파일을 읽고 쓴다면 이 테스트는 꼭 두세요.

## 단위 테스트로 안 되는 것: 진짜 프로세스 여러 개

이 도구는 AI 창마다 프로세스가 하나씩 붙어요. 창이 셋이면 프로세스도 셋이고, 셋이 같은 폴더의 기록 파일을 건드려요. 함수 하나를 부르는 단위 테스트로는 이 상황이 안 나와요.

그래서 스모크 테스트를 따로 두었어요. 흉내 낸 객체가 아니라 **진짜 stdio 프로세스를 여러 개** 띄워서 일감 만들기부터 마무리까지 한 바퀴 돌려요. 느리고 무겁지만, 배포 전에 한 번은 돌려요.

## 화면은 네 조합을 하나씩 열었어요

웹 화면은 HTML 파일 하나에 다 들어 있고, 자동 테스트가 없어요. 대신 UI 개편 때 절차를 정해 두었어요.

1. 배포 전에 스크립트 문법 검사 (`new Function` 으로 한 번 읽혀 보기)
2. 배포
3. 한국어·영어 × 연동·미연동, 네 조합을 하나씩 열어 확인

네 조합인 이유가 있어요. 문구는 언어에 따라 사전에서 바뀌고, 첫 화면은 연동 여부에 따라 아예 다른 카드가 떠요. 한국어·연동 상태만 보면 나머지 세 화면에서 빈 카드나 번역 안 된 문구가 나와도 몰라요. 개편 다섯 단계 중 마지막 단계가 통째로 이 확인이었어요.

## 통과와 실패

숫자는 git 기록에 남은 것만 적어요.

- 스프린트 기능을 넣은 시점: 테스트 3개 추가, 16개 통과
- 스킬·MCP 관리기를 넣은 시점: 테스트 3개 추가, 전체 19개
- 그 뒤 관리기 테스트 2개 추가, 지금은 전체 21개

실패도 하나 있었어요. 테스트가 남긴 임시 파일 하나가 기능 커밋에 섞여 저장소에 올라갔어요. 바로 다음 커밋이 그 파일을 지우는 커밋이에요. 테스트는 통과했는데 테스트가 어지른 자리를 안 본 거죠. 커밋 전에 바뀐 파일 목록을 한 번 읽으세요. AI가 커밋까지 해 주는 흐름에서는 이게 제일 쉽게 빠져요.

테스트 폴더가 배포 패키지에 딸려 가지 않게도 했어요. 패키지 설정의 `files` 에서 테스트 폴더 두 곳을 빼 두었어요.

## 검증에 쓴 명령

```bash
npm test          # 작업 보드 규칙 + 스킬·MCP 관리기 단위 테스트
npm run smoke     # 진짜 stdio 프로세스 여러 개로 한 바퀴
```

`npm test` 는 Node 에 들어 있는 테스트 러너(`node --test`)로 돌아요. 테스트 프레임워크를 따로 설치하지 않았어요. 로컬 도구를 의존성 없이 유지한다는 설계 약속을 테스트에서도 지킨 거예요.

## 아직 눈으로 보는 곳

화면이에요. 네 조합 확인은 사람이(또는 AI가 DOM 을 읽어서) 매번 다시 해야 해요. 그리고 스킬·MCP 관리기 계획서의 마무리 단계에 적어 둔 "스캔·마스킹·경로 검증 단위 테스트"는, 관리기를 처음 넣은 커밋에서는 아직 체크하지 않은 상태였어요. 세 개로 시작해 지금 다섯 개이고, 더 채워야 해요.

AI에게 기능을 시킬 때 이 한 줄을 붙이세요.

```
이 기능에서 깨지면 안 되는 규칙을 테스트 이름으로 먼저 적고, 그 테스트를 같이 만들어 줘.
테스트가 만든 임시 파일은 테스트가 지우게 해 줘.
```

규칙이 문장으로 남으면, 다음에 고칠 때 무엇을 지켜야 하는지 AI도 저도 다시 읽을 수 있어요.

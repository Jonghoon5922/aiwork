이번 주는 "아무도 손대기 싫은 옛 코드"와 "회의 녹음"처럼 사무실에서 늘 골치였던 일을 겨냥한 모델이 눈에 띄었어요. 그리고 AI 가 쓴 코드를 사람이 정말 이해하고 내보내는지 묻는 작은 도구도 하나 나왔어요.

### COBOL·Fortran 같은 옛 언어도 옮겨 주는 코딩 모델

출처: [OpenAI](https://openai.com/index/low-resource-programming-languages)

OpenAI 가 학습 자료가 적은 언어(COBOL, Fortran, Visual Basic, OCaml 등)에서 코딩 성능을 재는 평가 두 가지를 만들고 최신 모델 결과를 공개했어요. 20개 언어로 SQLite 호환 엔진을 만드는 MultiLangBench 에서 GPT-6 Astra 가 평균 87.4%(이전 세대 GPT-5.6 Sol 은 26.8%)를, COBOL 프로그램을 C++·Java·Kotlin·Python·Rust 로 옮기는 평가에서 GPT-6.1 Sol 이 낮은 추론 설정으로 86.6%, 높은 설정으로 97.9%를 기록했어요.

**써 볼 수 있어요** (개발자라면): 회사에 아무도 손대기 싫어하는 옛 코드가 있다면, 그중 작은 프로그램 하나를 골라 "동작을 그대로 보존하면서 Python 으로 옮기고, 반올림이나 빈 레코드 처리처럼 결과가 달라질 수 있는 지점을 표로 정리해 줘"라고 시켜 보세요. 글에서도 운영 코드에 적용하려면 전문가 검토와 업무 규칙 기준 테스트가 필요하다고 못 박았으니, 결과물은 바로 쓰지 말고 테스트 설계의 재료로 쓰세요. MultiLangBench 는 GitHub 에 공개돼 있어서 내가 쓰는 언어의 점수를 직접 확인할 수 있어요.

### 회의 녹음을 받아 적고 누가 말했는지까지 가리는 오픈 음성 모델

출처: [Hugging Face 블로그 (IBM Granite)](https://huggingface.co/blog/ibm-granite/granite-speech-5)

IBM 이 Granite Speech 5.0 2B 를 새로 내고, 기기에서 빠르게 돌리는 470M Turbo CTC 와 회의·통화용 4.1 2B Plus 를 갱신했어요. 셋 다 Apache 2.0 이고, 5.0 2B 는 영어·프랑스어·독일어·스페인어·포르투갈어·일본어를 받아 적으면서 제품명이나 사람 이름 같은 키워드를 최대 2,000개까지 넣어 오타를 줄일 수 있고, 4.1 2B Plus 는 화자 구분과 타임스탬프 정확도가 올라갔어요.

**써 볼 수 있어요** (직장인이라면): 한국어는 아직 지원 목록에 없어요. 그래도 영어 회의가 잦고 녹음 파일을 회사 밖 서비스에 올리기 꺼려졌던 분이라면, 사내 장비에서 돌릴 수 있는 선택지가 생긴 셈이에요. 가장 쉬운 첫걸음은 글에 링크된 Turbo CTC 의 브라우저(WebGPU) 데모에 영어 녹음 한 토막을 넣어 보는 거예요. 설치 없이 정확도를 가늠할 수 있어요. 개발팀에 부탁할 때는 "회의 녹음이면 4.1 2B Plus, 정확도가 먼저면 5.0 2B, 속도가 먼저면 Turbo CTC"라는 글의 선택 기준을 그대로 전달하면 돼요.

### Meta 의 공개 가중치 대형 모델은 코드와 화면 녹화를 같이 읽어요

출처: [Hugging Face 블로그](https://huggingface.co/blog/meta-muse-spark-open)

Meta 가 Muse Spark Open 을 공개 가중치로 냈어요. 전체 약 8,160억 개 파라미터 중 토큰마다 약 420억 개가 활성화되는 전문가 혼합(MoE) 구조이고, 텍스트·이미지·오디오·비디오를 입력으로 받아 텍스트를 내며 컨텍스트는 최대 100만 토큰이에요. 코드베이스 읽기, 디버깅, 도구 호출 같은 에이전트 코딩 작업에 맞춰 학습했고, BF16 체크포인트는 약 1.5TB, NVFP4 버전은 B200 한 노드에서 돌아간다고 해요.

**써 볼 수 있어요** (개발자라면): 노트북에서 돌릴 크기는 아니에요. 다만 같은 시리즈의 작은 모델 Muse Glimmer 가 로컬용으로 먼저 나와 있고 토크나이저와 채팅 템플릿을 공유하니, Glimmer 로 "이 스크린샷의 화면 오류를 재현하는 테스트를 써 줘" 같은 이미지 입력 코딩 프롬프트를 먼저 다듬어 두면, 나중에 Spark Open 을 호스팅 서비스에서 쓸 때 그대로 옮길 수 있어요. 오늘 할 일은 Hugging Face 모델 카드의 vLLM·llama.cpp 배포 레시피를 열어 우리 팀 GPU 로 가능한 구성인지 확인하는 것 하나예요.

### 법무팀의 접수 창구를 AI 로 바꾸려는 AT&T

출처: [OpenAI](https://openai.com/index/att-legal)

AT&T 법무 부서가 OpenAI 와 함께 자연어로 요청을 받는 접수 창구를 만들려고 해요. 들어온 요청을 분류하고 우선순위를 매긴 뒤 관련 선례·조사·과거 작업물을 붙여 담당 변호사에게 배경과 첫 조치 제안을 건네는 구조이고, 최종 판단은 변호사가 한다는 원칙을 분명히 했어요.

**써 볼 수 있어요** (직장인이라면): 법무가 아니어도 "요청이 메일과 메신저로 뒤섞여 들어오는 팀"이면 같은 구조예요. 오늘 받은 요청 다섯 건을 복사해서 AI 에게 "긴급도와 종류로 분류하고, 각 건에 담당자가 처음 확인해야 할 것 세 가지를 적어 줘"라고 시켜 보세요. 분류 기준이 마음에 들면 그것을 팀 접수 양식으로 굳히는 게 다음 단계예요. 회사 내부 문서를 넣을 때는 회사가 허용한 AI 도구인지 먼저 확인하세요.

### 내가 밀어 올리는 AI 코드를 정말 이해했는지 물어보는 Git 훅

출처: [Sphinx](https://sphinx-six-theta.vercel.app/)

Sphinx 는 보호한 브랜치에 push 할 때 멈춰 서서, 그 diff 가 실패 상황에서 어떻게 동작하는지 질문을 던지는 오픈소스 Git 훅이에요. 질문은 대화 기록을 보지 않은 별도 리뷰어 모델이 diff 만 읽고 만들고, 틀리면 이유를 알려 주며 다른 시나리오로 다시 묻고, 맞히면 push 가 이어져요. Codex·Claude Code·Cursor·OpenCode·Pi 와 같이 쓸 수 있고, 급할 때 건너뛰는 명령도 있지만 건너뛴 기록은 남아요.

**써 볼 수 있어요** (개발자라면): 에이전트가 쓴 코드를 "돌아가니까" 내보낸 적이 있다면 한 번 걸어 볼 만해요. Node 22.19 이상에서 `npm install -g sphinx-understand` 를 하고 `sphinx install` 로 Git 과 코딩 에이전트를 연결하면 끝이에요. 팀 전체에 강제하기보다 내 개인 저장소의 main 에 먼저 걸고 일주일 써 보세요. 질문에 자주 막히는 지점이 곧 내가 에이전트에게 설명을 더 요구해야 하는 지점이에요.

다음 주에 지켜볼 것: OpenAI 가 GitHub 에 공개한 MultiLangBench 에서 제가 쓰는 언어의 점수를 직접 열어 보고, 평가 문항이 실제 업무 코드와 얼마나 닮았는지 확인해 볼 생각이에요.
